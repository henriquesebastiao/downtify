# slskd 与 Navidrome

自托管音乐库可使用两项可选集成：

- **[slskd](https://github.com/slskd/slskd)**：通过自己的 slskd 服务器从 Soulseek 网络下载歌曲，作为 YouTube Music 和 YouTube 之外的音频来源。
- **[Navidrome](https://www.navidrome.org/)**：将下载的播放列表同步到 Navidrome，供任何 Subsonic 客户端使用。

两者均默认关闭，在**设置**中配置。

## 音频来源与备用顺序

**设置 → 音频来源**是有序列表。点击来源可添加或移除，选中多个时可用箭头调整顺序。每首歌曲依次尝试，在第一个提供音频的来源处停止：

| 来源 | 行为 |
|--------|-------------|
| **YouTube Music** | 默认来源。搜索 YouTube Music，没有合适匹配时回退到普通 YouTube，参见[工作原理](../how-it-works.md#fallback-to-standard-youtube)。 |
| **YouTube** | 只搜索普通 YouTube。 |
| **SoundCloud** | 默认关闭。搜索 SoundCloud；粘贴 SoundCloud 链接时下载对应的确切歌曲，参见 [SoundCloud](soundcloud.md)。 |
| **slskd** | 通过 slskd 搜索 Soulseek，并下载最佳匹配文件。 |

启用 slskd 会将其放在列表首位。若 slskd 成为唯一来源，之后仍会尝试 YouTube Music 和 YouTube，避免 slskd 找不到歌曲时无法下载。下载队列会显示每首歌曲的实际来源。

从搜索栏下载的歌曲会使用结果中的标题、艺人和时长，按相同顺序尝试各来源。选中的 YouTube Music 视频不会被固定为音频，因此 slskd 可以先提供其他版本或无损文件，再使用 YouTube 作为备用。

## slskd

### 配置

1. 运行 slskd，并为 Downtify 创建 API 密钥，详见 slskd 文档。
2. 将 slskd 的下载文件夹挂载到 Downtify 容器中，必须是 slskd 实际写入的同一宿主机文件夹，参见 [Docker Compose → 配合 slskd](../getting-started/docker-compose.md#with-slskd-soulseek)。
3. 在**设置 → slskd（Soulseek）**中启用 slskd，并填写：
    - **服务器地址**：两容器共用 Docker 网络时，例如 `http://slskd:5030`；
    - **API 密钥**；
    - **slskd 下载文件夹**：该文件夹在 *Downtify 容器内部*的挂载路径，默认 `/slskd`，不是宿主机路径。

启用 slskd 却未填写 URL 或 API 密钥时，保存会被拒绝并显示错误。

### 测试连接

保存前可点击字段下方的**测试连接**。测试使用表单当前内容，无论是否已保存，不修改任何数据。结果包括：

| 结果 | 含义 |
|--------|---------------|
| **已连接到 slskd 0.21.4。** | 地址正确，API 密钥已接受 |
| **slskd 已登录 Soulseek。** / **尚未登录** | slskd 自身是否已登录 Soulseek。未登录时无法搜索到内容；设置本身正确，因此显示警告 |
| **Downtify 可以读取 `/slskd`。** / **无法读取** | 上方下载文件夹在*当前*容器中是否存在且可读。警告通常是文件夹未挂载，参见[配置](#setup) |
| **slskd 拒绝了此 API 密钥。** | 服务器有响应，但不接受该密钥 |
| **无法连接…… / 未及时响应。** | 地址或端口错误、服务器未运行，或 Downtify 容器无法访问 |
| **似乎不是 slskd。** | 有服务响应，但不是 slskd；常见原因是端口错误，或地址缺少基础路径 |
| **HTTPS 证书不受信任。** | 在自己的网络使用 `http://`，或使用受信任机构签发的证书；Downtify 不会跳过证书检查 |

编辑任何字段都会清除上次结果，因为它已不再描述当前表单。地址和密钥都填写后，测试按钮才可用。

### 歌曲匹配方式

Downtify 使用标题和艺人搜索 slskd，按文件名和时长的匹配程度排序。默认优先匹配分数，格式顺序只用于同分情况。默认先 MP3 后 FLAC，并跳过报告比特率低于 256 kbps 的结果。总共最多逐个尝试五个候选。传输完成后，保留文件前会比对标签和时长。

在**设置 → 音频来源 → slskd**中，可将**格式优先级**设为 `flac, mp3` 等逗号分隔列表。开启**严格格式优先级**后，按顺序将各格式作为独立层级尝试，同一层级内仍按匹配分数排序。此时**候选尝试次数**按每种格式计算，因此 `5` 表示最多尝试五个 FLAC，再最多尝试五个 MP3。严格模式下，**有损格式的最低比特率**会拒绝低于阈值和未报告比特率的有损文件，FLAC 不受限制。

默认情况下，列表外的格式仍可作为最后一层候选。开启**仅允许列出的格式**可拒绝其他格式。关闭严格优先级时，白名单仍生效，正常的匹配分数优先行为不变。所有可接受的 slskd 候选失败或用尽后，会继续尝试下一个音频来源。

例如，设置 `flac, mp3`，开启严格优先级和白名单，将最低有损比特率设为 `320`，每种格式尝试五个候选，会先尝试 FLAC，再尝试至少 320 kbps 的 MP3。两层都失败时，再尝试下一个配置的来源。

非严格模式下，**有损格式的最低比特率**仍会跳过已报告较低比特率的文件，但允许未报告比特率的文件。

**质量方案**可自动填写格式列表：**默认**（`mp3, flac`）、**无损优先**（`flac, mp3`）或**仅有损**（`mp3, m4a, ogg, opus`，同时开启**仅允许列出的格式**）。之后可自由修改列表；与任何预设不一致时，不会突出显示方案。

开启**微调质量与匹配**可使用额外规则。关闭时不应用下列规则，但会保留设置值：

- **未标明比特率的文件**：**默认**保留上述规则，只在严格模式且设有最低值时拒绝。**允许**会在严格模式也接受，**拒绝**则在所有模式都跳过。
- **优先尝试最高比特率**：在达到匹配分数要求的文件中，优先最高比特率，而非最接近的文件名。
- **各格式最低比特率**：覆盖某种有损格式的最低值，例如将 `192` 用于 `m4a`，MP3 保持 `256`；留空则使用总体最低值。
- **最高比特率**：跳过超过此值的文件，`0` 表示关闭，约 `400` 可排除隐藏在 `.m4a` 中的无损 ALAC。

**候选尝试次数**、**总超时**和**排队超时**也位于此部分，无论额外规则开启与否均生效。

没有合适结果、传输未在**总超时**内完成，或在远端用户队列中无进展超过**排队超时**时，会继续尝试下一个音频来源。

**轮询与资源占用。**

请求的传输存在时，Downtify 每 5 秒轮询一次；slskd 中没有该传输时，每 60 秒一次，因此空闲传输最多需要 60 秒才反映到队列进度。超时仍限制总等待，空闲等待期间也会检查取消，不额外发送网络请求。

- `DOWNTIFY_POLL_INTERVAL`（默认 `5`）：活动轮询间隔，单位秒，范围 1–30。未设置时沿用 `poll_interval_seconds` 设置。
- `DOWNTIFY_POLL_IDLE_INTERVAL`（默认 `60`）：没有匹配传输时的间隔，单位秒，范围 1–60。
- `DOWNTIFY_TRANSFERS_TTL`（默认 `3`）：共享传输列表快照的有效期，单位秒，范围 0–60，`0` 关闭缓存。快照按服务器 URL 和 API 凭据隔离，最多 32 项，入队后失效，失败请求不缓存。
- `DOWNTIFY_POLL_DEEP_SCAN_EVERY`（默认 `12`）：传输不存在时，每 N 次轮询递归查找磁盘，范围 1–300。首次轮询和存在匹配传输的轮询也允许深度扫描；两次深度扫描之间的等待上限为 60 秒，避免空闲退避导致已完成文件十二分钟后才被发现。

每次轮询都会检查可预测的文件位置，节流只影响递归备用查找，包括重命名文件。最终备用扫描、标签匹配、被拒绝或失败传输的处理和来源回退均保留。退避不会放大原有尝试次数或时间预算。无效环境变量使用默认值，超范围值限制到有效边界。

`httpx` 和 `httpcore` 请求日志限制为 WARNING；`uvicorn.access` 也为 WARNING，除非使用 `--log-level DEBUG`。Downtify 自身的进度和失败日志仍可用。INFO 日志隐藏后，请求日志行数无法可靠衡量 HTTP 流量；比较请求频率时应使用 slskd 端访问日志或可计数的测试客户端。

### 将文件保留在原位

开启**将文件保留在 slskd 文件夹中**后（默认开启），下载文件留在 slskd 文件夹。Downtify 在原位写入元数据、封面和歌词，并以 `slskd/…` 路径登记到音乐库。音乐库、播放器和 M3U 均使用该路径，文件通过 `/media/slskd/…` 提供。

关闭后，文件会按文件名模板和[文件整理](file-organization.md)设置复制到其他下载旁。
副本写入标签并验证为可读音频后，Downtify 才会从配置的 slskd 来源文件夹删除原文件。复制、标签写入或验证失败时，原文件保留，下载报告错误。若删除原文件失败，已导入的音乐库文件仍算成功，并在日志中记录包含两个路径的警告。来源和目标是同一文件，或来源位于配置文件夹之外时，不会删除。已有遗留文件和失败的清理会单独计为 [slskd 工作副本](storage-usage.md#the-library-not-its-working-copies)。

::: info
slskd 文件保留原始格式，不会转换为设置中选择的格式。
:::

## Navidrome

### 配置

1. 确保 Navidrome 音乐文件夹包含 Downtify 下载文件夹；若保留 slskd 原位文件，也需包含 slskd 文件夹。Navidrome 扫描到歌曲后，才能将其加入播放列表。
2. 在**设置 → Navidrome**中启用 Navidrome，填写 URL、用户名和密码。
3. 可选填写**管理员**用户名和密码。Downtify 会在匹配新歌曲之前请求扫描音乐库，无需等待 Navidrome 自身的定时扫描。

### 测试连接

保存前点击字段下方的**测试连接**。测试使用表单当前内容，无论是否已保存，不做任何修改。结果包括：

| 结果 | 含义 |
|--------|---------------|
| **已连接到 navidrome 0.53.3。** | 地址正确，用户名和密码已接受 |
| **此账户可以发起音乐库扫描。** | 扫描账户具有管理员权限，使用填写的管理员用户名；未填写时使用普通登录账户 |
| **此账户无法发起音乐库扫描。** | Navidrome 只允许管理员扫描，但 Downtify 尝试时不会明确报告，新歌曲只会较晚出现。请填写管理员用户名和密码 |
| **管理员账户没有管理员权限。** | 所填管理员登录可用，但账户实际为普通用户 |
| **Navidrome 拒绝了管理员用户名或密码。** | 扫描账户凭据错误，主登录账户结果会单独报告 |
| **Navidrome 拒绝了此用户名或密码。** | 服务器有响应，但不接受该登录 |
| **无法连接…… / 未及时响应。** | 地址或端口错误、服务器未运行，或 Downtify 容器无法访问 |
| **似乎不是 Navidrome。** | 有服务响应，但不是 Subsonic API；常见原因是端口错误或地址缺少基础 URL |
| **HTTPS 证书不受信任。** | 在自己的网络使用 `http://`，或使用受信任机构签发的证书；Downtify 不会跳过证书检查 |

只查询扫描权限，测试不会实际启动扫描。编辑任何字段都会清除上次结果；地址、用户名和密码填写完整后，按钮才可用。

::: info 不会向页面返回敏感请求信息
响应只包含检测到的版本、路径和状态，不包含密码或 Downtify 发出的请求。
:::

### 播放列表同步

同步由管理员在设置 → Navidrome 中配置。普通账户不能创建同步配置，但集成开启后，其下载也会像其他人的下载一样同步。

开启**在 Navidrome 中创建播放列表**后，以下情况会创建或更新同名 Navidrome 播放列表：

- Spotify 播放列表下载完成；
- [播放列表监控](playlist-monitor.md)检查新增歌曲；
- 从音乐库删除歌曲，或[修复音乐库路径](library-catalog.md#fix-library-paths)。

歌曲优先按路径匹配 Navidrome，再按标签匹配。**将 Navidrome 播放列表设为公开**控制其在 Navidrome 中的可见范围。

Navidrome 也会将音乐文件夹内每个 M3U 导入为自己的播放列表，并使用旁边的封面，因此两种方式同时开启会让每个列表出现两次。开启**让 Navidrome 导入 M3U 播放列表**可只保留 Navidrome 导入：Downtify 改为请求重新扫描，不再创建播放列表，并移除此前创建的副本。**设置 → 医生**可查找并移除已有重复列表。

::: warning 标签与播放列表不匹配的文件会被删除
播放列表刷新时，例如删除歌曲、**修复音乐库路径**，或对已经完整的列表执行**下载缺失歌曲**，若登记到某个 Spotify 曲目的音乐库文件，其嵌入标题和艺人明显不匹配，会被**从磁盘删除**，因为 Downtify 将其视为错误下载。手动编辑标签时请留意。
:::

### 播放列表封面

无需额外配置：开启[保存播放列表封面](playlist-cover-art.md)后，只要 Navidrome 音乐文件夹覆盖该位置，就会将 Downtify 在 M3U 旁写入的 `.jpg` 作为**附属图片**读取，这是 Navidrome 自身解析列表封面的方式，不需要 Downtify 调用 API。

## 播放列表下载

**音乐库**页面的**播放列表下载**列出通过 Downtify 下载的 Spotify 播放列表。展开后，可比较音乐库已有歌曲数量与当前 Spotify 列表数量，并执行：

- **下载缺失歌曲**：只将尚未进入音乐库的歌曲加入队列；
- **播放**已下载歌曲；
- 展开列表，查看并下载单首缺失歌曲；
- **删除**播放列表，见下文。

### 删除播放列表

从此面板删除列表，或使用音乐库播放列表筛选器旁的**删除播放列表**，会从磁盘移除该列表登记的全部歌曲，**包括其他播放列表也包含的歌曲**，同时删除 M3U、旁边保存的[封面](playlist-cover-art.md)，并停止跟踪。共用这些歌曲的其他列表会在后台重写 M3U 和 Navidrome 播放列表。
